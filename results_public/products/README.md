# Inputs of the catalog build

`pipeline/catalog.py` (rule `catalog` in `pipeline/rules.py`) builds `../candidates_allsky.csv` and
`../tiers_earlier_candidates.csv` from the files here and `../overrides.csv`. It derives the TRICERATOPS columns
(`FPP` … `NFPP_gc`), `tier`, `c_reason`, `reported_as` and the flags, and takes the fitted columns from `fits.csv`
and the per-sector centroid columns from `centroids.csv`; every other column is copied from these files as written. The rules are listed at the top of `pipeline/catalog.py`, and their thresholds are in `pipeline/params.toml`.

| File | Contents | Made by |
|---|---|---|
| `measurements_allsky.csv`, `measurements_earlier.csv` | The measured columns of the two tables: transit fit, vetting, stellar parameters, pixel and per-sector centroid tests, binary and literature checks, the centroid Bayes factor `BF`, classifier scores, `rv_flag`, `set`, `search`, `candidate_id`. For the earlier searches also `base_tier` and `base_c_reason`: the label each signal was given when it was first listed (8 October 2026, or 12 October for the two added then), which it keeps unless a reason for tier C applies. | Copied from the published tables of commit b2a7d1f (15 October 2026). Some of the checks behind them cannot be rerun from what was kept (see below), so they are carried forward as published until the build recomputes them, one group of columns at a time. |
| `triceratops.csv` | For each catalog row with a TRICERATOPS result: the result it uses (`key`, `batch`), the inputs the result ran with (`period`, `t0_btjd`, `duration_h`, `depth_ppm`, `masks` of the star's other signals, scenario `drop`), the fold (`exptime_min`, `n_points`, `sectors`), and the means and largest values of the ten default-prior runs and of the ten Gaia-limited runs. `degenerate` = yes where TRICERATOPS did not evaluate the target (every scenario equally likely; the target has no TIC parallax). `lightcurves`: the hash of the light-curve list the fold was made from (empty for a legacy result, made from the searched list). `code`: the hashes of the code and packages of the result's stages (fold, target setup, MOLUSC, runs; empty for a legacy result). `runs_batch`: the batch that ran the runs, which differs from `batch` where a result was kept for a new request because its target setup came out the same. | `pipeline/triceratops_table.py` (rule `triceratops_table`) from the store of TRICERATOPS results (`pipeline/store.py`, `pipeline/tri_store.py`; not in the repository), each result under the hash of what determines it (`store`). The batches run before the store are imported as legacy results (`legacy` = yes): they did not keep their light-curve list, code version, and for all but the last batch their field-star population and MOLUSC file. A result is used only if it passes the checks of `pipeline/fpp_check.py`. |
| `triceratops_rejected.csv` | Newer TRICERATOPS results that fail a check made when the table is built, with the problem; the row then uses the signal's latest result that passes (for example, where the TIC has a duplicate entry at the star's position and TRICERATOPS took that entry, not the star, as its target). | `pipeline/triceratops_table.py` (rule `triceratops_table`). |
| `triceratops_batches.csv` | The TRICERATOPS batches run before the store, in the order in which a later batch's result for a signal replaces an earlier one; `pipeline/tri_store.py import` imported them. | By hand (complete). |
| `triceratops_plan.csv` | Every row whose tier can depend on TRICERATOPS (`needed` = yes, `catalog.needs_triceratops`) or that shows a TRICERATOPS result: the inputs a current result must have run with (ephemeris, depth, masks of the star's other signals and TOIs, scenario drops) and its status: `current`, `legacy` (current, from a legacy result), `pending` (needed, and missing or out of date) or `stale` (shown but out of date), with the reason. | `pipeline/tri_plan.py` (rule `triceratops_plan`). |
| `centroids.csv` | Per-sector centroid results measured after the copy of the measured columns: for each catalog row they cover, the measurement (`key`, `batch`), the ephemeris it used and the centroid columns, which replace the row's published ones. `code`: the hash of the measurement's code and packages (empty for a legacy entry). | `pipeline/centroid_table.py` (rule `centroid_table`) from the store (`pipeline/centroid_store.py`, entries of kind centroid; `store` is the entry), with centroid_test.py's test; each entry keeps the TIC dispositions of the stars near the target, so TIC artifacts and duplicates are never taken for neighbours. The batch in `centroid_batches.csv` was imported as legacy entries. |
| `centroid_batches.csv` | The centroid batches measured before the store, in order; `pipeline/centroid_store.py import` imported them. | By hand (complete). |
| `fits.csv` | For each catalog row with a transit fit: the fit it uses (`store`, `batch`, `legacy`), whether the fit passed its checks (`check`: a sampler that did not converge fails), and the columns it gives the row: `P_fit` (the published `P_d`), `P_err`, `T0_BJD`, `T14_h`, `Rp_Re`, `b`. A row whose fit failed has no fitted values. `lightcurves`: the hash of the light-curve list the fit was made from (empty for a legacy fit, made from the searched list). `code`: the hash of the fit's code and packages (empty for a legacy fit). | `pipeline/fit_store.py` (rule `fit_table`) from the store of fits; the fits made before the store were imported as legacy entries, each the fit file that reproduces the row's published values. New fits come from `pipeline/cloud.py plan --fits` (seeded, with the light-curve list, stellar row, steps and code recorded). |
| `spoc_2min.csv` | The re-measurement of each full-sky candidate's transits in SPOC's 2-minute light curves through Sector 96 (three noise estimates, transit and edge counts, SPOC TCEs on the star and on our transits), with the ephemeris (`P_d`, `T0_BJD`, `T14_h`) and sectors it used and the date (`measured`). The build keeps the rows of the current candidates with 2-minute data in `../../validation/spoc_2min_recheck.csv`. | `pipeline/spoc_recheck.py`, for the candidates the check `spoc_measured` lists (no measurement, or one made on another ephemeris or other sectors). The rows before 16 October 2026 are those of the published recheck tables of 12, 13 and 15 October, with the catalog's epoch of that day. |
| `tic_fields.csv` | Every star of the two tables whose TIC field (all TIC entries within 2′) has been checked, the date (`checked`) and the numbers of entries, galaxies and galaxy cores. | `pipeline/ticfield.py refresh`, a query of MAST run by hand (`--missing` checks only the stars not yet checked); the check `tic_fields_complete` fails while a star has no checked field. |
| `tic_nonstellar.csv` | The TIC entries near each star (`tic`) that cannot be the source of a transit-like signal although their light is real: extended sources (`kind` galaxy, from the 2MASS extended source catalog) and the point sources the TIC lists within 1″ of a galaxy without a parallax (`kind` core: the galaxy's core as Gaia saw it), with their separation and T magnitude. TRICERATOPS gives those within 31″ no scenarios, keeping their light in the aperture, and the per-sector centroid test does not take any of them as a possible source. TIC artifacts and duplicates are left out by their TIC disposition instead. | `pipeline/ticfield.py`, with `tic_fields.csv`. |
| `stage_code.json` | For each kind of stored result (`fold`, `tri_setup`, `molusc`, `tri`, `fit`, `centroid`), a hash of the stage's code now (the functions it runs, traced through imports) and of the lock file of its packages. A result whose `code` column names another hash for one of its stages was made by other code and is out of date. | `pipeline/stage_code.py` (rule `stage_code`). |
| `lightcurves_searched.csv` | For every star of the two tables, the light-curve products the searches used, one per sector: `sector`, source (`prov`: SPOC, TESS-SPOC or QLP), `exptime` (s) and the product's `uri` at MAST. Every result made before a MAST change was made from these. | `pipeline/lcindex.py` (rule `lightcurves_searched`) from the searches' light-curve lists: the QLP re-search's where it searched the star again, else the full-sky search's or the earlier searches'. |
| `lightcurves_current.csv` | The same stars' products at MAST on the date in `checked`: for each sector and source, the highest version. | `pipeline/lcindex.py refresh`, a query of MAST run by hand; the build then works out what it changes. |
| `lightcurves.csv` | The light curves new fits and TRICERATOPS folds use: `lightcurves_searched.csv` with each product that MAST has since replaced by another file of the same source (a redelivery, such as a new version) replaced by it, and without the sectors its source has withdrawn. Sectors that are new at MAST are not added; they need a search update. | `pipeline/lcindex.py` (rule `lightcurves`). The cloud runner reads the same lists, and each new result records the list it was made from. |
| `redo.csv` | Every catalog row on a star whose light curves have changed: the sectors whose product was `redelivered` or `removed`, the `new` sectors, the date of the MAST snapshot (`checked`) and the stages to redo (`redo`): `fit` and `TRICERATOPS` where the result in use was made from another list (the cloud runner redoes these), `search`, `vetting` and `pixel follow-up` (rerun by hand; they are not stored with their light-curve lists yet), or `search update` where only new sectors exist. `folder` = yes for rows with a candidate folder. Products are compared by file name, so a product replaced under the same name is not detected. | `pipeline/lcindex.py` (rule `redo`). |

`../overrides.csv` holds the decisions made by hand, one per row: the table, the signal (`TIC`, `P_d`), the column,
its value, the reason and where it is described. An override of `tier` or `c_reason` replaces the rules' outcome; an
override of any other column replaces an input before the rules run (for example `reported_as` for a community TOI
reported under another period).

Seven checks in `pipeline/rules.py` run on these inputs:
- `triceratops_current`: no row of `triceratops_plan.csv` is pending or stale (a result whose fold was made from a
  light-curve list other than the star's in `lightcurves.csv`, or whose stages ran code other than that in
  `stage_code.json`, is out of date);
- `fits_current`: no fit in `fits.csv` was made from a light-curve list other than the star's in `lightcurves.csv`, or
  by code other than that in `stage_code.json`;
- `centroid_inputs_current`: each centroid measurement in `centroids.csv` used the signal's current ephemeris and the
  code in `stage_code.json`;
- `tic_fields_complete`: every star of the two tables has a checked TIC field in `tic_fields.csv`;
- `centroid_neighbours_stellar`: no row's per-sector centroid test names a galaxy or a galaxy's core as the neighbour
  that fits;
- `counted_measured_centroids`: each counted candidate has per-sector centroid measurements;
- `spoc_measured`: each candidate with 2-minute data has a current re-measurement in `spoc_2min.csv`.

Inputs that no longer exist: the outputs of the literature, binary and RUWE checks behind the 726 rows of the first
full-sky release, the script that first wrote the earlier-search table, and some network answers that were not saved
(MAST dispositions, CDS cross-matches). The MOLUSC files and field-star populations of the TRICERATOPS runs were not
kept either.
